# Метод «ШАУРМА»

> **«Задачу можно слить. Шаурму — нет: каждую заворачивают заново, при тебе и по твоему заказу».**
>
> ШАУРМА — подход платформы «шаурматч_» к тестированию, категоризации и подбору ИТ-специалистов. Он закрывает два главных критерия ТЗ ФСП: механику подбора (35%) и механику тестирования, валидации и категоризации (25%).

---

## 0. Суть в одном абзаце

У всех существующих сервисов **тест, профиль кандидата и вакансия описаны на трёх разных языках**. Тест выдаёт балл, резюме — список слов, вакансия — текст. Поэтому подбор сводится к сравнению ключевых слов, а тест «прикручен сбоку».

ШАУРМА вводит **единое «Меню ингредиентов»**: каталог элементарных навыков ИТ-специалиста, например «граничные случаи», «асинхронность», «индексы БД», «сложность алгоритма». Один и тот же ингредиент одновременно:
1. **задаёт сложность задачи** — каждый ингредиент добавляет известную долю сложности (линейно-логистическая модель теста, LLTM);
2. **измеряется у кандидата** — у каждого ингредиента своя «температура освоения» (когнитивная диагностика по Q-матрице «задача → навыки» плюс рейтинг Glicko-2);
3. **заказывается работодателем** — вакансия превращается в «заказ»: какие ингредиенты нужны и в какой пропорции.

Задача, человек и вакансия оказываются **в одном пространстве**. Тест собирается по заказу, кандидаты ранжируются по тем же ингредиентам, которые проверял тест, а объяснение выдачи получается само: «из 5 ингредиентов заказа у кандидата подтверждены 4».

| Сервис | Что было | Чем закончилось и почему |

| **Vettery** | То же, кураторский отбор | Слился с Hired и ушёл в LHH |
| **Triplebyte** | Собственный технический скрининг и витрина проверенных инженеров | В 2023-м витрину закрыли, технологию тестов купила Karat. Погоня за объёмом размыла качество, плюс скандалы с приватностью |
| **RailsDevs** и другие «обратные доски» | Нишевые профили, компании платят за контакт | Профили «съедаются» наймом, нужно постоянно набирать новых, а доверие не масштабируется |
| **Otta, Cord, Underdog** | Профиль с ожиданиями, компании выходят на кандидата | Нет объективной проверки навыков |
| **getmatch, Хабр Карьера, hh.ru** (РФ) | Вакансии с открытыми зарплатами, база резюме, рекрутеры | Классический отклик. Работодатель всё равно вручную фильтрует отклики |

**Вывод:** обратный найм без **проверенных навыков** превращается в спам по базе, а площадка теряет кандидатов. Нужна проверка, которая сама поддерживает профиль «живым».

### 1.2 Проверка навыков
| Сервис | Подход | Слабое место |
|---|---|---|
| **LinkedIn Skill Assessments** | Фиксированные тесты с бейджами | **Закрыты в 2023-м**: ответы ко всем тестам лежали на GitHub. Это ровно та угроза, о которой пишет ТЗ |
| **CodeSignal, HackerRank, Codility** | Закрытый банк, ротация, прокторинг, мониторинг утечек | Утечку только замедляют, банк приходится держать в секрете вечно |
| **HackerRank, TestGorilla — «тест из описания вакансии»** | ИИ подбирает вопросы из библиотеки по тексту вакансии | Вопросы фиксированные. Сложность сгенерированных ИИ вопросов не откалибрована. Результат — общий балл, а не профиль навыков |
| **Karat** (бывший Triplebyte) | Адаптивные скрининги и интервью | Инструмент для компаний, а не витрина кандидатов. Дорого |
| **Хабр Карьера** | Тесты по навыкам → отметка в профиле | Фиксированные тесты, балл не связан с подбором |
| **Генерация задач нейросетью** | Каждому уникальная задача | Сложность несопоставима, ответ может быть галлюцинацией (ТЗ называет это прямо) |
| **Codeforces и спортивные рейтинги** | Объективный рейтинг, ценится частью рекрутеров | Мерит только спортивные алгоритмы, не связан с найм-процессом |
| **GapJumpers** («слепые прослушивания») | Анонимное задание = отклик | Инициатива у кандидата, компании не конкурируют за кандидата |

### 1.3 Что берём из науки (проверенные блоки)
- **Автоматическая генерация заданий (AIG)** — из одной «родительской» модели получают много вариантов.
- **LLTM (линейно-логистическая модель теста, Фишер)** — сложность задания = сумма сложностей его операций, поэтому сложность нового задания известна заранее.
- **Когнитивная диагностика (DINA, Q-матрица)** — из ответов восстанавливают, какие именно навыки освоены.
- **Адаптивное тестирование (CAT) и контроль частоты показа заданий** (randomesque, Sympson–Hetter).
- **Glicko-2** — рейтинг с неопределённостью, которая растёт при простое. На Lichess так калибруют шахматные задачи «игрок против задачи».
- **Canary trap** — разные версии документа, чтобы найти источник утечки. Плюс поиск «заранее известных» заданий по статистике ответов.

**Чего мы не нашли ни у кого:** чтобы эти блоки работали **в одном пространстве ингредиентов**, общем для задачи, кандидата и вакансии, внутри площадки обратного найма. Именно это и есть ШАУРМА.

## 2. Почему именно шаурма

| Шаурма | Метод |
|---|---|
| **Лаваш одинаковый у всех и лежит на виду** | Базовые шаблоны задач **открыты**. Секретов нет, сливать нечего |
| **Начинку кладут каждый раз заново** | Каждый кандидат получает **уникальный вариант**: мутации шаблона по своему seed |
| **Заворачивают при тебе, кухня открыта** | **Прозрачность:** кандидат видит рецепт (какие ингредиенты проверяются), работодатель видит, почему кандидат в подборке |
| **Готовится по заказу: «без лука, поострее»** | **Вакансия — это заказ.** Из неё собирается тест и регулярная задача |
| **В Москве шаурма, в Питере шаверма — суть одна** | **Изоморфные задачи:** разные названия и обёртки, одна и та же логика и сложность |
| **Вертел крутится без остановки, мясо срезают свежим** | **Рейтинг обновляется непрерывно.** Без активности «мясо остывает»: растёт неопределённость, и профиль опускается в выдаче |
| **У каждого ларька свой фирменный соус** | **Канарейки:** у каждого варианта свои метки, по ним видно, чья это «шаурма» |
| **Съеденную шаурму не перепродашь** | Вариант одноразовый: **ответ к чужому варианту бесполезен** и разоблачает списавшего |
| **У ларька все равны**: студент, сеньор, директор | **Слепой отбор** без вуза, возраста, пола, фото. Инклюзивность |
| **Еда хакатонов, ночных дедлайнов и программистов** | Понятна целевой аудитории, легко запоминается жюри |
| **Цена висит на табличке до заказа** | **Зарплата видна до начала общения** — принципиальное требование ТЗ |
| Бургер собирают заранее и держат под лампой | Обычный тест — заранее собранный набор, который «лежит» и протухает (сливается) |

И это просто акроним из шести частей метода:

| | Часть | Шаурма-термин |
|---|---|---|
| **Ш** | **Шаблоны** — открытый банк | Лаваш |
| **А** | **Адаптивная сборка по заказу** — вакансия → рецепт → адаптивный тест | Заказ |
| **У** | **Уникальная начинка** — мутации с известной сложностью | Начинка |
| **Р** | **Рейтинг на вертеле** — Glicko-2 по каждому ингредиенту | Вертел |
| **М** | **Матчинг вслепую** — «Слепая дегустация» и «Честный ценник» | Окошко ларька |
| **А** | **Антислив** — канарейки и статистика соответствия ответов | Фирменный соус |

## 3. Меню ингредиентов (ядро метода)

**Ингредиент** — элементарный, проверяемый навык. Справочник составляем сами (ТЗ это разрешает). Ингредиенты сгруппированы по специализациям:

| Группа | Примеры ингредиентов |
|---|---|
| Общие | Граничные случаи, сложность алгоритма, чтение чужого кода, отладка, тестирование |
| Backend | REST-контракты, транзакции и изоляция, индексы БД, очереди и идемпотентность, кэширование, конкурентность |
| Frontend | Состояние и рендер, асинхронность в UI, доступность (a11y), производительность рендера |
| Data / ML | Подготовка данных, утечка таргета, метрики качества, SQL-агрегации |
| DevOps | Контейнеры, CI/CD, наблюдаемость |

У каждой задачи есть **Q-строка**: какие ингредиенты она требует. Каждый **оператор мутации** добавляет ингредиент: например, «пустой вход» добавляет «граничные случаи», а «параллельный вызов» — «конкурентность».

## 4. Ш — Шаблоны: открытый лаваш

- Базовые задачи публикуются **открыто** вместе с разбором. Готовиться по ним честно и полезно.
- Шаблон — это задача с параметрами и точками мутации плюс Q-строка ингредиентов.
- Форматы на MVP (все проверяются автоматически):
  - **Чтение кода:** что выведет программа или какое значение вернёт функция.
  - **Найди дефект:** какая строка неверна и почему.
  - **Короткий код:** решение проверяется автотестами в песочнице.
  - **Подход к решению** (открытый ответ, используется в регулярных задачах): ИИ оценивает по рубрике, в рейтинг идёт с малым весом.

## 5. А — Адаптивная сборка по заказу

### 5.1 Вакансия → рецепт
ТЗ прямо просит показать, как по описаниям вакансий система формирует задания:
1. Работодатель пишет потребность обычным текстом.
2. ИИ (GigaChat / YandexGPT) раскладывает текст на **специализацию, грейд и вектор ингредиентов с весами**: «Нужен бэкендер на Go, highload, Kafka» → `очереди и идемпотентность 0.3, конкурентность 0.3, индексы БД 0.2, …`. Работодатель видит рецепт и может поправить веса ползунками.
3. Рецепт задаёт, какие шаблоны и мутации войдут в **регулярную задачу компании** и в **дополнительный блок теста** для подходящих кандидатов.

### 5.2 Первичный тест (обязательный путь по ТЗ)
1. **Опрос:** отрасль → специализация → стек.
2. **Самооценка:** кандидат сам выбирает предполагаемый грейд.
3. **Адаптивный тест:** старт у порога заявленного грейда. Следующее задание выбирается по максимуму информации **и покрытию ингредиентов специализации**. Частота показа задач ограничена: случайный выбор из 5 лучших заданий и лимит для каждого шаблона. Тест останавливается, когда точность достаточна, или после 12–15 заданий.
4. **Решение по грейду:**
   - P(уровень ≥ порог заявленного грейда) ≥ 0.55 → грейд подтверждён (порог подобран валидацией: максимум κ при доле завышенных грейдов < 6%);
   - P ≥ 0.8 для следующего грейда → кандидату сразу предлагается тест на повышение;
   - грейд не подтверждён → можно сразу пройти тест на уровень ниже. **Принудительного понижения нет.**
5. **Смена грейда — не чаще раза в 90 дней.**
6. **Категория = специализация × подтверждённый грейд** (`BE·MID`) — её видит работодатель. Стек и формат работы — фильтры, а не часть кода.
7. Побочный результат теста — **профиль ингредиентов**: какие навыки освоены и насколько уверенно.
8. **Банк заданий покрывает все грейды.** Шесть лёгких шаблонов (b ≈ −1.6…−0.6: срезы и словари в Python, filter/map и строки в JS, WHERE/ORDER BY/LIMIT в SQL, простой дефект) дают тесту точку опоры ниже порога Junior. Без них стажёру тест подбирал задания уровня Middle, и оценка была грубой.
9. **Несколько категорий.** После подтверждения основной категории можно добавить дополнительные, по одной на специализацию, — каждую своим адаптивным тестом (например, BE·SEN + DS·MID). У каждой категории свои правила: грейд не понижается принудительно, смена — не чаще раза в 90 дней. Рейтинги ингредиентов общие (SQL-навыки бэкендера засчитываются и в Data). Работодатель видит кандидата в подборке и банке каждой его категории, карточка открывается в разрезе специализации потребности. Смена основной специализации в опросе не переносит грейд: в новой специализации он есть, только если подтверждён тестом.

## 6. У — Уникальная начинка

Вариант = **шаблон + seed + операторы мутации + обёртка**.

| Слой | Пример | Кто делает |
|---|---|---|
| Параметры | Размеры входа, граничные значения | Детерминированный генератор по seed |
| Операторы мутации | Смещение на единицу (off-by-one), инвертированное условие, пустой вход, переполнение, параллельный вызов, другая структура данных | Детерминированный генератор |
| Обёртка («шаурма / шаверма») | Тот же алгоритм в контексте логистики, банка, турнира ФСП | GigaChat / YandexGPT, только текст |

- **Правильный ответ получается исполнением кода в песочнице, а не нейросетью.** Ошибка ИИ не может стать «правильным ответом».
- **Сложность варианта известна до показа (LLTM):**
  `b(вариант) = b(шаблон) + Σ η(оператор) + ε(обёртка ≈ 0)`.
  Сложности η операторов уточняются по накопленным ответам. Поэтому **разные кандидаты получают разные, но сопоставимые по сложности задания**. Это прямой ответ на проблему, которую ставит ТЗ.
- **Контроль обёртки:** после перефразирования вариант снова прогоняется через эталон и автотесты. Если смысл изменился, вариант отбрасывается.

## 7. Р — Рейтинг на вертеле

- Каждое решение — **матч «кандидат против задачи»**. Задачи тоже имеют рейтинг и калибруются онлайн, как шахматные задачи на Lichess, без отдельного предварительного прогона.
- **Glicko-2 считается по каждому ингредиенту**, а не одним числом. У каждого ингредиента три величины: сила μ, неопределённость RD и стабильность σ.
- **Мясо остывает:** без активности RD растёт, профиль теряет позиции. **Регулярные задачи** (из ТЗ) снижают RD, профиль снова «горячий». Так закрывается требование ТЗ об актуальности профиля.
- **Общая сила в категории** — консервативная оценка **μ − 2·RD** («кандидат не слабее этого»), взвешенная по ингредиентам специализации.
- **Достижения ФСП** засчитываются как внешние подтверждённые матчи по ингредиентам дисциплины. Например, продуктовое программирование даёт «REST-контракты», «командную разработку», «граничные случаи». Вес зависит от уровня соревнования, места и роли.
- **Без истории ФСП штрафа нет:** профиль подтверждается тестами. В интерфейсе нейтральная пометка «Подтверждено тестами платформы».

## 8. М — Матчинг вслепую

### 8.1 Подборка по заказу (основной путь по ТЗ)
```
Score(кандидат | заказ) = Σ_i  w_i · Mastery_i(μ_i − 2·RD_i)      ← совпадение ингредиентов
                        × Fit(стек, формат, ожидания по зарплате)  ← жёсткие условия и стек
                        × (1 + бонус ФСП)
```
- Выдача строится из **категорий, присвоенных тестом**, а не из резюме (требование ТЗ).
- **Объяснение у каждой позиции:** «из 5 ингредиентов заказа у кандидата подтверждены 4. Самый сильный — идемпотентность (топ-10%), слабее — индексы БД. Грейд подтверждён 2 мес. назад. Призёр ФСП».
- Фильтры уточняют запрос **без потери подборки**: заказ сохраняется, фильтры накладываются поверх.
- **Приглашение:** описание, зарплата «от–до» в ₽ (обязательно), компания, способ связи. Статусы: отправлено → просмотрено → принято / отклонено. Контакты раскрываются только после принятия.

### 8.2 «Слепая дегустация»
1. Работодатель публикует для категории **регулярную задачу**, собранную по его заказу. У каждого кандидата при этом своя начинка.
2. Кандидаты решают анонимно. Результат идёт в рейтинг на вертеле, мясо снова горячее.
3. Работодатель **пробует решения через «окошко ларька»**: видит решение, разбор по ингредиентам и рейтинг, но **не видит, кто автор**. Понравилось — отправляет приглашение с вилкой зарплаты.
4. Если «заказали» несколько компаний, кандидат видит **«Очередь из 3 компаний: 280–320, 300–350, 330–380 тыс. ₽»** и выбирает сам. Сила переходит к кандидату, компании конкурируют условиями.
5. Слепой отбор убирает предвзятость по возрасту, вузу, полу и инвалидности. Это прямая связь с инклюзивностью платформы.

### 8.2a «Свежая начинка» — адресная задача от системы
ТЗ описывает регулярную задачу как то, что **система периодически предлагает кандидату**. Поэтому, кроме задач от работодателей, шаурматч_ сам раз в 7 дней адресно подбирает каждому кандидату с подтверждённой категорией короткую задачу:
1. **Какой ингредиент.** Тот, которому подтверждение нужнее всего: рейтинг «остыл» (давно не было практики, RD вырос), ингредиент ещё ни разу не проверялся или это самое слабое место относительно грейда. Кандидат видит причину: «Рейтинг „REST-контракты" остыл: 220 дн. без практики — работодатели видят его ниже».
2. **Какая задача.** Шаблон и начинка, которые покрывают этот ингредиент, со сложностью чуть ниже уровня кандидата (≈65% успеха): так ответ максимально информативен и не демотивирует. Уже решённые шаблоны не повторяются.
3. **Оценка автоматическая.** Вариант уникален, эталон получен исполнением кода, результат — «матч» на вертеле. Задача приходит при заходе в «Задачи» и письмом (периодический обход раз в 6 часов). Работодатель видит в карточке кандидата, что тот поддерживает форму («практика шаурматч_»).

Код: `engine/app/practice.py` (выбор), `backend/src/services/practice.ts` (когда и кому), миграция `003_system_tasks.sql`.

### 8.3 «Честный ценник» (защита от фиктивных вакансий — «будет плюсом» в ТЗ)
- **Талоны на приглашения:** у компании ограниченное число приглашений в неделю. Лимит растёт с репутацией. Талон возвращается, если кандидат ответил. Массовая рассылка невыгодна, и это лечит болезнь, которая сгубила обратные площадки.
- **Ценник не врёт:** после собеседования кандидат одним кликом подтверждает, совпала ли зарплата с заявленной вилкой. Если нет, у компании падает репутация, урезаются талоны, и бейдж «Честный ценник» снимается.
- **Признаки фиктивности:**
  - вакансия висит месяцами без найма;
  - все приглашения с одинаковым текстом;
  - вилка сильно выше рынка (приманка);
  - много приглашений, ни одного найма.
- **Интеграция с внутренними системами подбора компаний (ATS) — концепция:** приглашения и статусы отправляются вебхуками и выгружаются в Хантфлоу, Potok, E-Staff.

### 8.4 Что видит работодатель и как читать выдачу
- **Кольцо «совпадение»** — P(подойдёт): вероятность, что кандидат пройдёт собеседование по этому заказу (ранжировщик «Маринада»). **Порядок** — шанс найма = P(подойдёт) × P(примет приглашение с вашей вилкой); вторая часть показана рядом («примет ≈72%» и что мешает). Место в выдаче и процент считаются одной моделью и не спорят друг с другом.
- **ФИО, опыт и места работы видны по умолчанию** (ответ организаторов VS.4: закрываются только контакты). Кандидат может скрыть имя и места работы — тогда он «Кандидат #код». Анонимность остаётся принципом «Слепой дегустации».
- **Стек: со слов и подтверждённый.** «✓ Python» — кандидат решил не меньше двух заданий на этом языке сложностью не ниже уровня своего грейда. Простая доля верных не годится: адаптивный тест держит её около 60% у всех. Остальной стек — со слов кандидата; это фильтр, а не часть категории.
- **Резюме — подсказка, а не категория.** Разбор PDF извлекает ФИО, контакты, стек, роли, места работы с периодами, стаж и софт-скиллы; собственная языковая модель шаурматч_ подсказывает специализацию и навыки для предзаполнения опроса. Категорию и место в выдаче определяет только тест.

### 8.5 Как распространить метод на дизайнеров (концепт)
Организаторы допускают дизайнеров в справочник, если есть объективная проверка (WA.2). ШАУРМА переносится без изменения ядра:
- **Лаваш** — макет интерфейса (форма, карточка, таблица), сгенерированный кодом по шаблону.
- **Начинка** — операторы-нарушения гайдлайна с известной сложностью η: контраст ниже 4.5:1, сломанная сетка на 4 px, неверный порядок фокуса, «висящий» заголовок, разные радиусы у однотипных элементов.
- **Задание** — «найди нарушение»: варианты ответа — области макета. Эталон известен, потому что нарушение внесено генератором; проверка контраста и сетки вычисляется, а не оценивается на глаз.
- **Ингредиенты** — доступность, сетка и типографика, визуальная иерархия, консистентность дизайн-системы. Рецепт вакансии «продуктовый дизайнер B2B» раскладывается на них так же, как для разработчиков.

## 9. А — Антислив: фирменный соус

- **Канарейки:** в каждом варианте уникальные метки — константы, имена, порядок данных, иногда «ловушка», правильная только для этого варианта. Если в ответе кандидата Б есть ответ к варианту кандидата А, это **доказательство списывания** и источник утечки.
- **Статистика соответствия ответов модели (person-fit):** трудные задания решены, лёгкие провалены, аномально быстрые ответы. Такая попытка отправляется на перепроверку.
- **Проверка пониманием:** при подозрении кандидат получает 2–3 уточняющих вопроса по своему решению (ИИ-интервью).

## 11. Валидация (обязательный раздел сдачи)

Готовых данных нет, поэтому строим **синтетический мир с известной истиной**:

1. **2 000 синтетических кандидатов** с заданными истинными уровнями по ингредиентам, специализацией, стеком и (у 40%) историей ФСП. Ответы моделируются по моделям LLTM и IRT, а ИИ генерирует правдоподобные резюме.
2. **Тест:**
   - восстановление грейда: точность и Cohen's κ между истинным и присвоенным грейдом;
   - **тест-ретест** на разных вариантах: согласованность грейда;
   - восстановление профиля ингредиентов: корреляция с истиной;
   - дискриминативность заданий: точечно-бисериальная корреляция, информация задания;
   - **симуляция слива:** 30% кандидатов знают весь банк и ответы чужих вариантов. Сравниваем завышение грейда (фиксированный тест против ШАУРМЫ) и долю пойманных канарейками.
3. **Подбор:** 60 описаний вакансий и размеченные пары «вакансия — кандидат» (по истине, часть проверяется вручную). Метрики **Precision@10 и nDCG@10** в сравнении с поиском по ключевым словам (BM25) и поиском по эмбеддингам резюме.
4. **Главный слайд питча:** «Слили весь банк задач: обычный тест завышает грейд, ШАУРМА — нет». Цифры появятся после прогона симуляции.

## 11a. «Маринад»: метод учится на собственных данных

Экспертные числа метода (сложности b0 и η, дискриминация, словарь «слово → навык», веса подбора)
заменяются моделями, которые дообучаются на действиях пользователей. Ответы на задания калибруют тест
(LLTM + 3PL, MML-EM со страховочным шлюзом). Детектор «чёрствого лаваша» замечает, что приём начинки «утёк».
Правки рецептов учат собственную языковую модель. Ответы на приглашения и итоги собеседований учат
двусторонний ранжировщик P(подойдёт) × P(примет).

В симуляции «года жизни платформы» завышенных грейдов стало на 30% меньше, наймов на одно приглашение —
на 37% больше, а «утёкший» приём пойман за 123 ответа без ложных тревог.
Подробно: [МАРИНАД.md](МАРИНАД.md), страница `/marinade`.

## 12. Объём MVP
- **Обязательно:** меню ингредиентов (3 специализации × ~8 ингредиентов), 25–40 шаблонов, 10–15 операторов мутации, адаптивный тест, Glicko-2, заказ → рецепт, подборка с объяснением, приглашения, канарейки, скрипт валидации.
- **Плюсом:** «Слепая дегустация», талоны и «Честный ценник», отклики на вакансии, мобильная версия.
- **Концепт для питча:** ИИ-агенты, ИИ-интервью, интеграция с ATS, найм команд.
