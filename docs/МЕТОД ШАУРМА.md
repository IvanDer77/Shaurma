# Метод «ШАУРМА»: механика тестирования и подбора

ШАУРМА — подход платформы «шаурматч_» к тестированию, категоризации и подбору ИТ-специалистов. Документ описывает реализованную механику, её параметры и обоснование устойчивости к распространению заданий. Все числа соответствуют коду в репозитории; результаты проверки приведены в разделе «Валидация метода».

Название — акроним шести частей метода: **Ш**аблоны, **А**даптивная сборка, **У**никальная начинка, **Р**ейтинг, **М**атчинг, **А**нтислив. Образ тоже выбран по существу: задание, как шаурму, собирают заново для каждого кандидата по одному и тому же открытому рецепту.

---

## 1. Суть метода

В существующих сервисах тест, профиль кандидата и вакансия описаны на трёх разных языках: тест выдаёт балл, резюме — список слов, вакансия — текст. Поэтому подбор сводится к сравнению ключевых слов, а результат теста не участвует в поиске.

ШАУРМА вводит **единый справочник навыков («ингредиентов»)**. Один и тот же ингредиент одновременно:

1. **задаёт сложность задания** — каждый оператор изменения шаблона добавляет известную долю сложности (линейно-логистическая модель теста, LLTM);
2. **измеряется у кандидата** — по каждому ингредиенту ведётся рейтинг Glicko-2 с неопределённостью;
3. **заказывается работодателем** — описание потребности превращается в рецепт: какие ингредиенты нужны и с каким весом.

Задание, кандидат и потребность оказываются в одном пространстве. Тест собирается из тех же ингредиентов, по которым потом ранжируются кандидаты, а объяснение выдачи следует из модели напрямую: «подтверждено 5 из 9 ингредиентов заказа».

## 2. Аналоги и выводы из них

### 2.1. Обратный найм
| Сервис | Подход | Итог |
|---|---|---|
| Hired, Vettery (США) | Компании направляют кандидатам приглашения на интервью с зарплатой | Объединены и в 2024 году свёрнуты в LHH. Проверки навыков не было, модель держалась на перегретом рынке |
| Triplebyte | Собственный технический скрининг и витрина проверенных инженеров | В 2023 году витрина закрыта, технология тестов продана Karat |
| Otta, Cord, Underdog | Профиль с ожиданиями, компании выходят на кандидата | Нет объективной проверки навыков |
| getmatch, Хабр Карьера, hh.ru | Вакансии с зарплатами, база резюме | Классический отклик, работодатель вручную фильтрует входящий поток |

**Вывод.** Обратный найм без проверенных навыков превращается в рассылку по базе, и площадка теряет кандидатов. Нужна проверка, которая сама поддерживает профиль в актуальном состоянии.

### 2.2. Проверка навыков
| Сервис | Подход | Слабое место |
|---|---|---|
| LinkedIn Skill Assessments | Фиксированные тесты с бейджами | Закрыты в 2023 году: ответы ко всем тестам были опубликованы |
| CodeSignal, HackerRank, Codility | Закрытый банк заданий, ротация, прокторинг | Утечку только замедляют, банк нужно держать в секрете постоянно |
| Тесты, собранные из библиотеки вопросов по тексту вакансии | Автоматический подбор вопросов | Вопросы фиксированные, результат — общий балл, а не профиль навыков |
| Автоматическая генерация задания под каждого кандидата | Уникальное задание каждому | Сложность заданий несопоставима, корректность ответа не гарантирована |
| Codeforces и спортивные рейтинги | Объективный рейтинг | Измеряет только алгоритмическую подготовку и не связан с наймом |

### 2.3. Научные основания
- **Автоматическая генерация заданий (AIG)** — множество вариантов из одной родительской модели.
- **LLTM (линейно-логистическая модель теста)** — сложность задания равна сумме сложностей его операций, поэтому сложность нового варианта известна заранее.
- **Адаптивное тестирование (CAT)** с контролем частоты показа заданий.
- **Glicko-2** — рейтинг с неопределённостью, которая растёт при отсутствии активности.
- **Canary trap и статистика соответствия ответов модели (person-fit)** — выявление списывания.

Новизна метода — в том, что эти блоки работают в одном пространстве ингредиентов, общем для задания, кандидата и потребности, внутри площадки обратного найма.

## 3. Термины

| Термин | Значение |
|---|---|
| Ингредиент | Элементарный проверяемый навык, например «Граничные случаи» или «SQL JOIN» |
| Лаваш | Открытый шаблон задания с параметрами и точками изменения |
| Начинка | Набор операторов изменения, применённый к шаблону; определяет уникальный вариант |
| Рецепт | Потребность работодателя в виде ингредиентов с весами |
| Вертел | Рейтинг Glicko-2 по каждому ингредиенту, который обновляется после каждого ответа |
| «Слепая дегустация» | Регулярная задача работодателя, решения которой он видит без имён |
| «Честный ценник» | Механизм защиты от недобросовестных работодателей |
| Канарейка | Признак того, что ответ взят из чужого варианта |

## 4. Справочник специализаций, грейдов и ингредиентов

Справочник составлен командой (ТЗ, п. 2). Грейды: **Intern, Junior, Middle, Senior**. Категория кандидата — связка специализации и подтверждённого грейда, например `BE·MID`. Стек и формат работы — фильтры, а не часть категории.

| Специализация | Код | Ингредиенты |
|---|---|---|
| Backend-разработка | BE | Чтение чужого кода, Граничные случаи, Сложность алгоритмов, Поиск дефектов, Идемпотентность и повторы, Конкурентность и асинхронность, Изменяемое состояние, REST-контракты и пагинация, SQL-агрегации, SQL JOIN |
| Frontend-разработка | FE | Чтение чужого кода, Граничные случаи, Поиск дефектов, Event loop и промисы, Замыкания и области видимости, Иммутабельность состояния, Типы и приведение в JS, Методы массивов, REST-контракты и пагинация |
| Data / ML | DS | Чтение чужого кода, Граничные случаи, Сложность алгоритмов, SQL-агрегации, SQL JOIN, Оконные функции, Работа с NULL, Метрики качества моделей, Подготовка данных и утечки |

Всего 19 ингредиентов; общие ингредиенты засчитываются во всех специализациях, где они есть. Код: `engine/app/ingredients.py`.

## 5. Ш — открытый банк шаблонов

- В банке **34 шаблона**: 27 заданий «что выведет код» (Python — 11, JavaScript — 11, SQL — 5) и 7 заданий «найди дефект» (Python — 4, JavaScript — 2, SQL — 1). Шесть шаблонов намеренно лёгкие (сложность от −1,6 до −1,2 логита), чтобы тест точно оценивал уровень ниже Junior.
- У каждого шаблона задана строка ингредиентов, которые он проверяет, и перечень допустимых операторов изменения.
- Все задания имеют четыре варианта ответа и проверяются автоматически.
- Банк можно публиковать открыто: знание шаблона не даёт ответа на конкретный вариант (раздел 6).

Код: `engine/app/templates/`.

## 6. У — уникальный вариант

Вариант задания = **шаблон + зерно генератора + набор операторов изменения + контекст**.

| Слой | Что меняется | Как |
|---|---|---|
| Параметры | Размеры и значения входных данных | Детерминированный генератор по зерну |
| Операторы изменения | Смещение границы на единицу, инвертированное условие, пустой вход, повторный вызов, другая структура данных и другие; всего 72 оператора и 123 допустимых набора | Детерминированный генератор |
| Контекст | Тот же алгоритм в одной из пяти предметных областей: логистика, банк, соревнования ФСП, поддержка, аналитика | Подстановка имён и формулировки |

**Правильный ответ получается исполнением сгенерированного кода** (Python, Node.js, SQLite), а неверные варианты — исполнением типичных ошибочных версий. Ошибочный эталон исключён по построению.

**Сложность варианта известна до показа:**

`b(вариант) = b(шаблон) + Σ η(оператор)`

Поэтому разные кандидаты получают разные, но сопоставимые по сложности задания. Начальные значения b и η заданы экспертно и уточняются по накопленным ответам (раздел 12).

Код: `engine/app/generator.py`, `engine/app/runner.py`.

## 7. А — адаптивный тест и категоризация

Обязательный путь кандидата (ТЗ, п. 2):

1. **Опрос:** отрасль, специализация, стек.
2. **Самостоятельный выбор грейда.**
3. **Адаптивный тест.**
   - Модель ответа — трёхпараметрическая логистическая (3PL), оценка уровня — ожидаемое апостериорное значение (EAP).
   - Старт — от центра заявленного грейда.
   - Следующее задание выбирается по максимуму информации с учётом покрытия ещё не проверенных ингредиентов специализации.
   - Контроль частоты показа: случайный выбор из пяти лучших заданий и штраф для часто показываемых шаблонов. В проверке ни один шаблон не показывался чаще 4,3% случаев.
   - Длина теста — **от 8 до 18 заданий**: тест останавливается, когда стандартная ошибка оценки не превышает 0,40.
4. **Решение по грейду:**
   - вероятность того, что уровень не ниже порога заявленного грейда, не меньше 0,55 — грейд подтверждён (порог подобран на валидации);
   - вероятность для следующего грейда не меньше 0,8 — кандидату предлагается тест на уровень выше;
   - грейд не подтверждён — можно сразу пройти тест на уровень ниже. **Принудительного понижения нет.**
5. **Смена подтверждённого грейда — не чаще одного раза в 90 дней.**
6. **Несколько категорий.** После подтверждения основной категории кандидат может добавить категории в других специализациях, каждую отдельным тестом. Рейтинги общих ингредиентов учитываются во всех категориях. Смена основной специализации не переносит грейд: он появляется только после теста.
7. Побочный результат теста — **профиль ингредиентов** кандидата.

Категория, которую видит работодатель, определяется только этим путём. Данные резюме используются для предзаполнения опроса и на категорию не влияют.

Код: `engine/app/cat.py`, `backend/src/routes/tests.ts`.

## 8. Р — рейтинг по ингредиентам

- Каждый ответ — «матч» кандидата против задания известной сложности. Рейтинг **Glicko-2** ведётся по каждому ингредиенту: сила μ, неопределённость RD и волатильность σ.
- Без активности RD растёт, и консервативная оценка кандидата снижается. Регулярные задачи (раздел 10) возвращают её обратно. Так выполняется требование ТЗ об актуальности профиля.
- **Сила профиля внутри категории** — консервативная оценка `μ − 2·RD`, усреднённая по ингредиентам специализации, плюс надбавка за призовые места ФСП.
- **Достижения ФСП** учитываются как внешние матчи по ингредиентам дисциплины. Сила «соперника» зависит от уровня соревнования: от 1450 (городской) до 1850 (международный). Призовое место или попадание в лучшие 20% засчитывается как победа, в лучшие 50% — как ничья.
- **Отсутствие истории ФСП не снижает позицию.** Достижения только добавляют информацию; профиль без них подтверждается тестами.

Код: `engine/app/glicko.py`.

## 9. М — подбор и выход на контакт

### 9.1. Из потребности в рецепт
1. Работодатель описывает потребность обычным текстом.
2. Текст раскладывается на специализацию, грейд, стек, вилку зарплаты и ингредиенты с весами. Разбор выполняют словарь предметной области и собственная текстовая модель платформы (символьные n-граммы, линейные классификаторы). Для каждого ингредиента показывается фрагмент текста, по которому он найден.
3. Работодатель может изменить веса и параметры рецепта; подборка пересчитывается. Правки используются для дообучения модели разбора.

Внешние языковые сервисы для работы не требуются. При наличии ключей GigaChat или YandexGPT их ответ может использоваться для уточнения весов рецепта и разбора резюме; контактные данные в такие сервисы не передаются.

### 9.2. Ранжирование
Выдача формируется только из кандидатов с категорией, присвоенной тестом, и согласием на публикацию профиля.

```
Совпадение(кандидат, рецепт) = Σ w_i · Освоение_i(μ_i − 2·RD_i)  # ингредиенты рецепта
                             × Соответствие(грейд, стек, формат, зарплата)
                             × (1 + надбавка ФСП, не более 15%)
```

Для ранжирования берётся консервативная оценка `μ − 2·RD` относительно центра требуемого грейда; показываемый процент совпадения считается по `μ − RD` относительно нижней границы грейда. Порядок выдачи определяет двусторонний ранжировщик: **вероятность, что кандидат подойдёт, умноженная на вероятность, что он примет приглашение** с указанной вилкой. Работодатель видит обе величины. Если ранжировщик недоступен, используется формула выше.

### 9.3. Объяснение выдачи
У каждого кандидата указано, почему он в подборке: сколько ингредиентов рецепта подтверждено, какой из них самый сильный, какие не подтверждены, совпадение стека, давность подтверждения грейда, достижения ФСП, соответствие ожиданий по зарплате.

### 9.4. Фильтры и банк кандидатов
Фильтры по грейду, стеку и наличию достижений ФСП накладываются поверх сохранённой потребности, подборка при этом не теряется. Отдельно доступен поиск по всему банку кандидатов с фильтрами по специализации, грейду, стеку и достижениям ФСП.

### 9.5. Приглашение
- Приглашение содержит описание, **вилку зарплаты «от–до» в рублях (обязательно)**, название компании и способ связи. Привязка к опубликованной вакансии не обязательна.
- При составлении приглашения работодатель видит, покрывает ли вилка ожидания кандидата.
- Статусы: отправлено, просмотрено, принято или отклонено. При отказе кандидат указывает причину; причины сводятся в статистику работодателя.
- **Контактные данные кандидата открываются работодателю только после принятия приглашения** или самостоятельного отклика кандидата на вакансию.
- В приглашении кандидат видит, по каким подтверждённым навыкам он выбран.

### 9.6. Что видит работодатель до согласия кандидата
Категорию, рейтинги ингредиентов, стек (с пометкой, какие технологии подтверждены заданиями теста), достижения ФСП, ожидания по зарплате, опыт из резюме. Имя и места работы показываются, если кандидат не скрыл их в настройках приватности; иначе выводится «Кандидат #код».

### 9.7. «Честный ценник»: защита от недобросовестных работодателей
- **Недельный лимит приглашений:** `5 + репутация / 10`. Лимит освобождается, когда кандидат ответил на приглашение. Массовая рассылка становится невыгодной.
- **Подтверждение зарплаты:** после принятия приглашения кандидат отмечает, совпала ли зарплата на собеседовании с вилкой. Ответ «нет» снижает репутацию компании на 25 пунктов; при репутации ниже 75 снимается отметка «Честный ценник», которую видят все кандидаты. Ответ «да» повышает репутацию на 2 пункта.

Код: `engine/app/recipe.py`, `engine/app/matching.py`, `engine/app/learn/ranker.py`, `backend/src/routes/employer.ts`, `invitations.ts`.

## 10. Регулярные задачи

Раз в 7 дней кандидату с подтверждённой категорией адресно предлагается короткая задача.

1. **«Слепая дегустация».** Если есть открытая задача работодателя для категории кандидата, предлагается она. Задача собирается по рецепту потребности; у каждого кандидата свой вариант. Кроме ответа кандидат может описать подход к решению. Работодатель видит решения без имён, с категорией и рейтингом автора, и может пригласить автора с вилкой зарплаты.
2. **«Свежая начинка».** Если задач работодателей нет, система сама подбирает задание по ингредиенту, которому подтверждение нужнее всего: рейтинг давно не обновлялся, ингредиент ещё не проверялся или он слабее остальных. Сложность выбирается немного ниже уровня кандидата.

Результат в обоих случаях обновляет рейтинг ингредиентов. Задача появляется в разделе «Задачи» и приходит письмом.

Код: `backend/src/services/practice.ts`, `engine/app/practice.py`, `backend/src/routes/tasks.ts`.

## 11. А — защита от распространения заданий

**Почему утечка банка не даёт преимущества.**
1. Шаблоны открыты: скрывать нечего.
2. Вариант уникален: ответ зависит от зерна и набора операторов. Ответ на чужой вариант к своему не подходит.
3. Сложность вариантов сопоставима (LLTM), поэтому оценки разных кандидатов сравнимы.
4. Эталон получен исполнением кода, поэтому заученный «ответ на шаблон» неверен для изменённого варианта.

**Выявление списывания.**
- **Канарейки.** Если ответ кандидата совпал с правильным ответом чужого варианта того же шаблона, это фиксируется как признак использования чужих ответов.
- **Соответствие ответов модели (индекс lz).** Профиль «трудные задания решены, лёгкие провалены» статистически маловероятен; при lz ниже −2 попытка помечается.
- **Скорость.** Три и более ответов быстрее 6 секунд также помечают попытку.

Помеченная попытка сохраняется в отчёте сессии для проверки; автоматической блокировки нет.

Результаты проверки на модели полной утечки банка приведены в разделе «Валидация метода»: фиксированный тест завышает грейд списывающих на 1,32 уровня, предложенный метод завышения не даёт, канарейки выявляют 91,5% таких попыток при 1,3% ложных срабатываний.

Код: `engine/app/antileak.py`.

## 12. Самообучение («Маринад»)

Экспертные параметры метода уточняются по данным самой платформы: ответы кандидатов калибруют сложность шаблонов и операторов, правки рецептов дообучают модель разбора текста, ответы на приглашения и итоги собеседований дообучают ранжировщик. Отдельный детектор замечает, что вариант стал аномально лёгким, то есть его разбор распространился. Подробно — в разделе «Маринад».

## 14. Ограничения и развитие

- Банк покрывает три специализации. Метод переносится на другие направления добавлением ингредиентов и шаблонов; для дизайнеров проработан концепт заданий «найди нарушение в макете», где нарушение вносится генератором и потому проверяется автоматически.
- Текст подхода к решению в регулярных задачах пока оценивает работодатель; автоматической оценки нет.
- Проверка помеченных попыток выполняется вручную.
- Интеграция с ATS работодателей и верификация компаний описаны в разделе «Архитектура» как концепция.
